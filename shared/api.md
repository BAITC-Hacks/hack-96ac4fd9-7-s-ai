# API CONTRACT — единственный источник правды

## Идея (1-2 предложения)
Клиент задаёт параметры своего мероприятия (город, дата, тип, категория подрядчика,
бюджет), сервис возвращает до 3 карточек подрядчиков с объяснением, почему каждый
подходит — на основе бюджета, языка, длительности и описания, а не общих фраз.

## Demo — сценарий показа жюри (3 минуты)
1. Клиент открывает форму, вводит город, дату, тип мероприятия, категорию, бюджет.
2. Нажимает «Найти подходящих» → видит до 3 карточек с конкретным объяснением каждой.
3. Меняет дату на занятую → часть кандидатов пропадает, в объяснении видно почему (заняты).
4. Вводит редкую категорию → видит все 1-3 доступных или честное «таких нет в этом городе».
5. Вау-момент: карточки не взаимозаменяемы — у каждой своя причина, привязанная к факту
   из профиля, а не рейтинг/проценты «на глаз».

## Общее
- База: `/api`. Ответ всегда `ApiResponse<T>` (см. `types.ts`).
- Все поля camelCase, даты в формате ISO-строки, ID — строки.
- Бюджет — это порог (`price_from_kzt <= budgetKzt`), а не сигнал качества: дешевле не
  значит хуже, дороже не значит лучше.
- Детерминизм обязателен: одинаковый `CreateMatchInput` → одинаковый порядок карточек
  при повторном запросе.

## Эндпоинты

### GET /api/health
→ `ApiResponse<{ status: 'up' }>`

### GET /api/catalog-options — списки для формы (город/категория/формат/язык)
→ `ApiResponse<CatalogOptions>`
Строится из датасета на старте бэка, чтобы фронт не мог отправить несуществующую
категорию/город (расхождение написания kz/ru в датасете — частая причина багов).

### POST /api/match — найти подходящих подрядчиков
Body: `CreateMatchInput`
→ `ApiResponse<MatchResult>` (синхронно, цель — до 10 секунд)
Ошибки: `VALIDATION` (не заполнено обязательное поле: city/eventDate/eventType/category/budgetKzt)

Логика на бэке (не меняется без согласования):
1. Жёсткие фильтры кодом (не LLM): занятость на `eventDate` по `busy_dates`,
   `city`, `category`, `price_from_kzt <= budgetKzt`, затем если заданы — `language`,
   `durationHours` (с учётом `max_hours`), `eventType` входит в `event_formats`.
2. Если после фильтра 0 кандидатов в этом городе+категории вообще — `status: 'no_category'`.
3. Если есть кандидаты, но ни один не прошёл фильтр по остальным условиям —
   `status: 'no_match'`, `message` объясняет, что именно не совпало.
4. Иначе `status: 'found'`, выбираются до 3 кандидатов по детерминированному правилу
   (релевантность description/формату, при равенстве — сортировка по `id`), `candidatesBeforeCut`
   передаёт, сколько всего прошло фильтр (для честного «показаны все 2 из 2»).
5. Объяснения для отобранных карточек генерируются одним batch-вызовом AI (все карточки
   сразу, не по одной) — так объяснения естественно различаются между собой и укладываются
   во времени. При сбое/таймауте AI — объяснение собирается из фактов без LLM (фолбэк-шаблон),
   ответ всё равно приходит вовремя.
