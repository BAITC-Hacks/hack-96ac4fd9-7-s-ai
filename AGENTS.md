# AGENTS.md — общие правила для ВСЕХ ИИ-агентов

Хакатон, 5 часов. Задача: «умный подбор подрядчиков» (#79-lite) — сервис принимает
параметры мероприятия (город, дата, тип, категория подрядчика, бюджет) и возвращает
до 3 карточек подрядчиков с конкретным объяснением, почему каждый подходит. Ценность —
в объяснении, а не в сортировке. Полный текст задачи и датасет — у людей, вопросы по
условиям (что считается «сайт занят», какие категории редкие и т.п.) — им, а не наружу.
Скорость важнее идеальности, но код в ветке **всегда рабочий**.

Схема простая: **один Codex на зону**. FRONT — один агент в `frontend/`, BACK — один агент
в `backend/`. Никаких параллельных суб-агентов в одной папке (гонки за файлы, порты,
`node_modules`) — не оправдано на 5 часов и 2 людей. Агент сам себе планировщик и кодер:
роль описана в `roles/DEV.md`. Тестировщик (`roles/TESTER.md`) отдельный и запускается
только на чекпоинтах и в финале, в отдельной папке `<repo>-main`.

## Перед любой работой прочитай
1. `CONVENTIONS.md` — стек, имена, форматы. Нарушать нельзя.
2. `shared/api.md` и `shared/types.ts` — контракт между FRONT и BACK.
3. Свою роль в `roles/` (тебе её назовут в первом сообщении: DEV или TESTER).
4. `TASKS.md` своей зоны, если уже создан.

## Зоны (жёстко)
- FRONT-агент пишет **только** в `frontend/`.
- BACK-агент пишет **только** в `backend/`.
- `shared/`, `CONVENTIONS.md`, `AGENTS.md`, `roles/`, `scripts/` доступны **только для чтения**.
  Нужно изменить контракт? Допиши предложение в `<своя_зона>/CONTRACT_REQUEST.md` и продолжай
  работу на старом контракте. Контракт меняют люди.

## Запрещено
- `git commit`, `git push`, `git merge`, `git rebase`, `git reset`, `git checkout` — git делают только люди.
- Менять `.env`, коммитить ключи, выводить ключи в лог.
- Переименовывать или удалять то, что экспортировано из `shared/`.
- Большие рефакторинги, смена библиотек, «улучшения» вне задачи.

## Критерий «готово»
Задача считается готовой, если `npm run typecheck` (и `lint`, если есть) в своей зоне проходит,
фича вручную работает, а `TASKS.md` обновлён. Непроверенный код готовым не считается.

## MVP прежде всего
Первая половина работы — не «сколько фич успеем», а «полный путь пользователя end-to-end,
пусть просто». Порядок задач в `TASKS.md` всегда: сначала то, что нужно для демо-сценария
целиком, потом полировка и доп. фичи. Точные времена — в `HOW-TO.md`.
